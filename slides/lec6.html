Vibe coding

Vibe coding

Vibe coding is a new paradigm where the programmer’s “vibe” or intention drives the AI’s code generation, relying on prompt iteration and output testing rather than traditional code authoring and review

What is vibe coding?

Natural Language Input : Programmers describe their requirements in everyday language, like “build a user login page.” AI then translates this into functional code, often without the developer looking at or editing the generated code directly.

AI as Coding Partner : The human role focuses on guiding, testing, and providing feedback, rather than worrying about implementation details and syntax. The process is often iterative—adjustments are made by refining the instructions rather than the code.

Acceptance Without Full Understanding : True “vibe coding” means embracing the AI’s suggestions without thorough manual review or understanding of the codebase, in contrast to traditional pair programming or code-completion tools where the developer remains tightly involved with the output.

Faster Prototyping : Vibe coding accelerates app building, making it possible for those with less coding experience to develop complex software rapidly.

Risks and Criticisms : While this method opens software development to more people and speeds up prototyping, there are concerns about maintainability, accountability, and security—especially since developers might deploy code they do not fully understand.

Typical Vibe Coding Workflow

State what’s needed in plain English

Let the AI generate, test, and refine the code

Repeat and iterate by updating prompts or goals

Focus on output and function, not on syntax or structure

RAGs introduction

Retrieval-Augmented Generation

LLM - challenges

LLMs generate answers using static training data, which can be outdated or incomplete

Training data is not up to date

Difficulties with use of data that are dynamic

Why RAGs?

Access to Up-to-Date Information: Unlike static models, RAG allows AI to provide recent, domain-specific, or company-private data without retraining.

Better Factual Accuracy: By grounding responses in retrieved documents, RAG reduces “hallucination” (fabrication of information) common in non-augmented LLMs.

Flexibility: RAG can be adapted to many domains (education, legal, medical, business) and is the foundation for applications like smart document assistants and chatbots

Approaches to provide current data

Fine tuning

  • Retrain layers of the LLM with current data
  • Time consuming
  • Hard to keep LLMs up to date if data changes often

RAGs

  • Adds data to the LLMs context window

RAG

The retriever

Locates and extracts pertinent data from external sources using keyword search or vector similarity search

The retriever retrieves the information to be fed to the generator e.g. search engine, vector database, …

The (user) query is used to retrieve the data

The augmentation

The retrieved data is added to the query/prompt 

The generator

The LLM retrieves the original query plus the retrieved data, i.e. the augmented data/prompt

RAG Architecture and Process

Indexing/Preparation : External data is pre-processed and turned into numerical embeddings (vectors), often stored in a vector database for efficient retrieval.

Retrieval : On receiving a query, the system converts the query into an embedding and retrieves relevant documents or data chunks from the vector store.

Augmentation : The retrieved information is placed in the prompt using prompt engineering templates, making it available to the model during generation.

Generation : The LLM produces its output by combining its internal knowledge with the retrieved, up-to-date context, leading to more truthful and current responses

Embeddings ( Indexing/Preparation)

Embeddings are numerical representations of text, allowing models to compare meaning and context.

Example: “Coffee” and “Espresso” have similar embeddings; “Coffee” and “Cat” are far apart

These representations are stored in a vector database

Why Do We Need Embeddings in RAG?

Problem : Pure keyword search can miss context and semantic meaning.

Embeddings power semantic search : retrieve relevant content even if different words are used.

Embeddings make RAG powerful and accurate.

The Embedding Workflow in n8n

Fetch data (text files, docs, etc.)

Use n8n’s embedding node to convert text chunks into vectors.

Optionally, enrich with metadata (title, source, section).

Store vectors in a vector database like Qdrant .

Qdrant as a Vector Store

What is Qdrant ? Open-source vector DB for similarity search at scale.

How it works: Store and index embeddings efficiently; support for billions of vectors.

Benefits for us/education: Open-source, easy n8n integration, fast retrieval.

n8n + Qdrant Integration Overview

Basic workflow:

Data loader → Embedding model node → Qdrant (Insert) node.

  • e.g. load file, embed file, insert in vector DB

Practical choices:

  • Embedding model selection (OpenAI, HuggingFace , etc.)
  • You need a model to embed your data with
  • You need the same model to retrieve it

Configuring chunk size and metadata

  • Find out what chunk size the model is using and have the vector DB match it

Querying and Retrieval

“User” question is embedded (turned into a vector via n8n).

Qdrant performs similarity search: finds vectors (text chunks) closest to the query in embedding space.

Matched content is sent back to n8n and LLM for answer generation.
