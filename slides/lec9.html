Issues with Naïve RAGs

Loss of Context : When you split documents into independent chunks, you sever the relationships between them.

Difficulty with Comparative Questions : Answering questions like “What are the differences between Product A and Product B?” is hard.

Redundancy and Noise : You often retrieve multiple chunks that say roughly the same thing, or chunks that are only tangentially related to your query. This adds noise for the LLM to sift through.

“Shallow” Retrieval : Vector search is great at finding explicit information but struggles with implicit relationships. It won’t know that “MIT” is a “university” located in “Cambridge” unless that’s explicitly stated in the retrieved chunk.

What is a graph?

A graph is a data structure that models entities and the relationships between them

  • It is not a chart or coordinate system!

Nodes -  the primary “things” or nouns in your data.

Examples:

  • Person: “Dr. Eva Core”
  • Company: “InnoTech”
  • Project: “Helios”
  • Concept: “Machine Learning”

Relations - t he connections that give context to the nodes.

They are directed and labeled to describe the relationship.

Examples:

  • WORKS_AT
  • DEVELOPED
  • IS_PREREQUISITE_FOR

Graph RAGs

Based on graphs instead of vectors

Instead of a simple list of text chunks, we first build a Knowledge Graph.

This graph explicitly stores entities (like people, products, concepts) as nodes and the relationships between them as edges.”

Building the graph

This isn’t just about embedding text.

It’s about extracting structured information from unstructured text.

We identify the key entities and how they connect.

For example, from the sentence ‘Dr. Eva Core developed the ’Helios’ project at InnoTech,’ we extract three nodes (Eva Core, Helios, InnoTech) and two relationships (DEVELOPED, WORKED_AT).”

ETL for Graph RAGs

Extract :

Entity Extraction: Use models (e.g. LLMs) to identify key entities (people, organizations, locations, topics, etc.) in your documents.

Relationship Extraction: This is the crucial part. Identify the verbs or phrases that connect these entities. For example, “Company X acquired Company Y,” “Person A is the CEO of Company B.”

Transform :

Schema Definition: Define your graph schema. What types of nodes will you have (e.g., Person, Company, Project)? What types of relationships (WORKS_FOR, ACQUIRED, TOPIC_OF)?

Data Cleaning & Normalization: Standardize entity names (“MIT” and “Massachusetts Institute of Technology” should be the same node).

Load :

Populate the Graph Database: Use a graph database like Neo4j to load the extracted nodes and relationships. This creates the persistent, queryable knowledge graph that the RAG system will use..

Using the graph DB

Query Transformation: The user’s natural language question (“What are the main features of Project Helios?”) is transformed into a formal graph query (e.g., Cypher for Neo4j). This can be done using an LLM.

  • Example Cypher Query: MATCH ( p:Project {name: ‘Helios’})-[:HAS_FEATURE]->( f:Feature ) RETURN f.name

Graph Traversal & Retrieval:

  • The graph DB executes this query, retrieving not just a single piece of text, but a structured subgraph of related information.
  • You might retrieve the project node, its features, the team members who worked on it, and links to related documentation.

Context Augmentation:

  • This structured information is then serialized into a clean, readable format and passed to the LLM as context, along with the original question. The LLM gets a pre-digested summary of all the relevant, interconnected facts.

Example of use

The RAG in Action:

  • Naïve RAG Query : “Which courses should I take after Databases?” A vector RAG might return the description of the advanced database course, but that’s it.
  • Graph RAG Query : Ask the same question. Show how the Graph RAG transforms this into a Cypher query: MATCH (:Course {name: ‘Databases’})-[:IS_PREREQUISITE_FOR]->( c:Course ) RETURN c.name.
  • The Result : The Graph RAG will definitively list all courses that have Databases as a prerequisite. It can also pull in their descriptions, providing a complete and accurate answer that the vector search might miss.

Use case -  Code base navigation

Nodes : Functions, Classes, Files, Modules, Developers

Relationships : CALLS (function A calls function B), DEFINED_IN (function is defined in a file), IMPORTS (file imports a module), AUTHORED_BY (developer wrote a function).

Questions  

  • What does the calculate_metrics function do?” (The system should retrieve the function’s docstring and the code itself).

“Who has modified the user_authentication.py file the most?” (Requires traversing AUTHORED_BY relationships and aggregating the data).

  • “Show me all the functions that call the database.connect () function.” (A classic use case that is very hard for vector search but trivial for a graph query).
